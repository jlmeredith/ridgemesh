# RidgeMesh

Terrain-aware communication planner for Astral Valley, Missouri. Compute the best placement found for an available fixed-radio inventory, then scale the radio budget and customize locations, roles and antenna heights for roaming users. **All coverage is an uncalibrated planning estimate.**

## What is implemented

- Immutable USGS 1 m source terrain resampled to a declared 10 m analysis grid, one NAD83 UTM spatial contract, contours and ground-relative antenna heights.
- Two real Sentinel-2 acquisitions (June and November 2024), plus high-detail USDA NAIP aerial photography (June 2022), synchronized swipe comparison and textured 3D with cardinal cameras.
- Event locations reconciled against official 2023–2025 maps and visible aerial features: the western Family camp, central Stargazer hilltop, eastern Harmony/Dreamcatcher areas and southern Main Stage. One versioned registry supplies labels, target areas, starter positions and placement candidates.
- Applied computed starting network: the owned Seeed P1 solar as ROUTER at Stargazer and an assumed camp radio as fixed CLIENT_BASE at Harmony Grove. Two Wio Tracker L1 Pro handhelds are a roaming count, with no invented positions. Budget controls recompute the whole unlocked infrastructure; unused stock stays in reserve. The opening view is actual-scale 3D with all layers and landscape signal heat enabled. A visible workbench compares the recommended network, R1 without fixed support and alternate primary sites; Customize edits radios directly.
- Existing custom and deliberately empty plans survive reload. The exact previous untouched starter upgrades with a backup; loading the optimized plan explicitly preserves the previous plan for restoration. Unreadable saved data is preserved before autosave can replace it.
- Directed RF budgets, terrain/Fresnel/diffraction profiles, explicit forwarding roles, separate return paths and a filled 40 m two-way signal-margin field across the landscape. Event-area scores retain their original denominator. The MediumFast baseline uses a derived −126 dBm receiver threshold; custom legacy plans retain their prior RF assumptions.
- The mandatory P1 site/height search compares stage, Stargazer and other permitted sites; a bounded beam adds useful fixed support radios. Optional offered Station G3/5.8 dBi equipment and additional community counts are explicit inputs. Budget and alternative-site results use the same 40 m target samples as displayed coverage. Totem is removed from the app and RF model.
- Minimum tested mast-height guidance raises one endpoint while keeping the other fixed, with separate ground line-of-sight, 60% Fresnel clearance and bidirectional RF requirements.
- Worker calculation/cancellation, schema 3 inventory and scenario JSON roundtrip, browser persistence, physical-device locks, keyboard placement and undo, field-walk export and held-out observation review. Previous-format imports preserve original bytes before removing retired equipment.

## Run and verify on the remote host

Node 24 and npm 11 are pinned; use `npm ci`. No tests, builds, browser automation or GIS processing run on the Mac. From a worktree, `npm run check:remote` transfers a snapshot and runs installation, typecheck, lint, tests and build on z370. See `scripts/remote-check.sh` for recorded revision/run provenance. Run the application on a remote host with `npm run dev`; tunnel its port if needed.

Browser verification: run `timeout 480 node scripts/terrain-scenarios-browser-check.mjs` on z370 with `RIDGEMESH_RUN_ID`, `RIDGEMESH_REVISION` and optionally `RIDGEMESH_BROWSER_URL`. Its acceptance checks cover actual-scale 3D, all default layers, filled heat and physical scenario changes, reversible preview/apply, direct movement/height editing, budget scaling, optional equipment, physical identities, original-file recovery, actual imagery textures and mobile; inspect the report for the exact executed count. Earlier browser harnesses preserve historical release evidence and have outdated UI assumptions. Screenshots must pass `scripts/normalize_screenshot.py` before viewing.

Regenerate `public/data/optimized-plan.json` only on z370 with `npx tsx scripts/generate-starter-plan.ts`. Its versioned scenario and evidence come from the same bounded optimizer, site/height policy, RF engine and event-area targets used by the interactive planner; an integration test detects stale output.

Vercel uses the TanStack Start framework, Nitro Vercel preset, Node 24 and `npm run build`; no database, map-provider secret or server GIS process is needed. Derived imagery/data are committed with provenance; raw source GIS is retained on z370.

## Evidence and limitations

[Current WBS](docs/TERRAIN-SCENARIOS-WBS.md), [current release record](docs/TERRAIN-SCENARIOS-RELEASE-2026-09-13.md), [AstralMesh recommendations](docs/ASTRALMESH-PLANNING-RECOMMENDATIONS-2026-09-13.md), [preceding equipment contract](docs/INVENTORY-PLANNER-RELEASE-2026-09-13.md), [preceding planner correction](docs/PLANNER-CORRECTION-RELEASE-2026-09-13.md), [event-map reconciliation](docs/evidence/event-map-registration-20260913.md), [height/placement evidence](docs/evidence/planner-domain-correction-20260913.md), [terrain evidence](docs/evidence/terrain-delivery-20260912.md). The [first recovery release](docs/RECOVERY-RELEASE-2026-09-12.md) is historical; its venue geometry and blanket coverage presentation were rejected and are superseded by the correction.

Camp-use boundaries and land cover remain interpreted; 25–80 m feature allowances are judgments, not measured survey accuracy. No legal property boundary, installation permissions or calibrated canopy model is supplied. The P1 module and stock antenna values are sourced; modem sensitivity, configured output, generic camp hardware and unverified handheld antenna gains remain editable assumptions. Offered equipment locations need owner confirmation. The simplified RF model does not certify packet delivery, capacity, GNSS availability or installation feasibility. Real field observations are required for calibration. The current infrastructure optimizer exhausts P1 site/height choices, then keeps six support-search states; it is not a global optimum. Two-access-node coverage does not establish survival of a failed primary P1. CLIENT_BASE favorites/timing are setup records, not simulated packet priority. Schema 3 carries inventory and the site version; schema 2 supported custom radios migrate with an original-file backup. Incompatible site/terrain data remain recoverable rather than being silently reinterpreted.
